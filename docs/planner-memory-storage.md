# Хранилище памяти планировщика

Модуль: planner_memory.py. Самостоятельный блок, не подключённый к Telegram и расчёту поставок. Он хранит данные опыта; не обучает веса модели, не выполняет текст инструкций и не меняет правила расчёта автоматически.

## Файлы

- data/planner_memory.sqlite3 — отдельная постоянная SQLite, не база Excel деклараций.
- data/planner_memory-ledger.md — локальный машинный архив с читаемым обзором.
- docs/planner-memory.md — читаемая сводка знаний; её нельзя передать в restore_markdown как машинный архив.
- docs/planner-memory-ledger.md в репозитории бота и knowledge/wb-fbo-memory-ledger.md в ai-knowledge — одинаковые резервные копии машинного архива, которые сохраняет ассистент.

SQLite сохраняется при обычном перезапуске. Локальная копия обновляется при изменениях, если backup_path передан в конструктор; удалённые копии обновляет ассистент без токена GitHub в боте. Успех обеих публикаций проверяется отдельно повторным чтением и сравнением содержимого.

## Интерфейс

MemoryStore(db_path, backup_path=None) получает явные пути, не читает .env и не обращается к сети. propose(text, reason=..., scope=..., target=..., expires_on=..., kind=...) создаёт неподтверждённую запись и возвращает UUID. confirm(id), reject(id), revoke(id) сохраняют изменения состояния в истории. Повтор того же перехода безопасен; конфликтующий переход отклоняется.

Области: global, product с точным target и plan с точным ID черновика. kind=rule обозначает правило, kind=case — пример решения. Пример не превращается в обязательное правило. applicable(product=..., plan_id=..., on_date=...) возвращает подтверждённые подходящие записи; срок действует включительно, дата по умолчанию московская. history() сохраняет и отклонённые, и отменённые записи.

## Экспорт и восстановление

export_markdown() возвращает строку; write_backup() атомарно записывает архив в указанный путь. Архив версии1 содержит ровно один машинный JSON-блок и контрольную сумму SHA256. Контрольная сумма выявляет повреждение, но не заменяет доверие к источнику.

Для восстановления создать MemoryStore по НОВОМУ пути в постоянном каталоге и вызвать restore_markdown(archive_text). Проверяется весь архив до вставок. В пустую базу восстанавливается полная история; одинаковая история даёт unchanged без дублей; отличающаяся непустая база вызывает ConflictError. Автоматического объединения историй, замены повреждённой базы или импорта произвольных рукописных заметок нет.

При потере основного файла восстановление сначала проверять в отдельной базе и сверять history()/entries(). Не заменять работающую базу до проверки и отдельной копии. В начальном архиве события отражают текущую загрузку ранее согласованных правил; прежняя переписка не выдается за восстановленный журнал событий.

## Сбои и ограничения

BackupError.saved=True означает: изменение УЖЕ сохранено в SQLite, не записалась Markdown-копия. Использовать entry_id из ошибки, затем повторить write_backup(); не повторять propose вслепую. Конструктор не затирает резервную копию пустым состоянием. Служебные файлы SQLite не могут быть целью резервирования.

Ограничения этой версии: 10000 событий, архив до2MB, текст/причина до4000 знаков. Исчерпание лимита останавливает запись, история не обрезается молча. Слияние расходящихся архивов, Telegram-интерфейс, автоматический GitHub и применение памяти к прогнозам относятся к следующим этапам.

Начальная загрузка проверена: 11 ранее подтверждённых правил, один пример решения, 24 события. Все107 тестов прошли; независимые PASS расчёта и памяти сохранены в .ai/task. Код модулей пока только в локальной ветке, работающий бот не перезапускался.
